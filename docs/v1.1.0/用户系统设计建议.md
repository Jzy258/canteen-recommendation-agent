# 用户系统设计建议（管理员 + 用户）

> 版本：v1.1.0　|　日期：2026-08-04　|　维护：A（数据与算法）
> 状态：**D8a + D8b 已实施**（认证闭环 + user_id 数据隔离）· D8c（管理端）待实施
> 依据：`docs/DESIGN.md`、`backend/db/schema.sql`、`backend/main.py`、`backend/auth/`
> 对应 schema 变更：`backend/db/schema.sql`（v1.1 增量迁移，已实现）

---

## 1. 现状与关键约束

当前系统是**单用户架构**：

| 维度 | 现状 |
|------|------|
| `user_profile` | 单行，无用户归属，`store/profile.py` 只读"最近一条" |
| `meal_record` | 无 `user_id` 列，无法区分记录归属 |
| 会话 | 靠 `session_id`（uuid），无账号概念，登录态不持久 |
| 权限 | 无角色概念，所有接口匿名可访问 |
| 认证 | `/chat`、`/trend`、`/records`、`/metrics` 均无鉴权 |

**核心约束**：

1. `schema.sql` 是 A 的唯一来源，B/C 的 `store/record` 工具只读此 schema，**任何表结构变更须走增量迁移**，避免重建库丢失数据
2. `meal_record` / `user_profile` 加 `user_id` 涉及现有全部查询路径（A 的聚合、B 的记录工具、C 的趋势图），改动面最大
3. 现有匿名 `session_id` 交互模式被前端（localStorage 会话）依赖，建议保留为"游客模式"

## 2. 数据模型设计

### 2.1 新增表：`app_user`

```
CREATE TABLE IF NOT EXISTS app_user (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    username      TEXT    NOT NULL UNIQUE,               -- 登录名（唯一）
    password_hash TEXT    NOT NULL,                      -- 密码哈希（PBKDF2-SHA256，salt 内嵌）
    role          TEXT    NOT NULL DEFAULT 'user'        -- 角色：admin / user
                       CHECK (role IN ('admin','user')),
    display_name  TEXT    DEFAULT '',
    status        INTEGER NOT NULL DEFAULT 1,            -- 1=启用 0=禁用
    created_at    TEXT    NOT NULL DEFAULT (datetime('now','localtime')),
    last_login_at TEXT
);
```

### 2.2 业务表增量迁移（关键决策点）

对现有表增加用户归属列，SQLite 通过 `ALTER TABLE ADD COLUMN` 实现，配合
`SQLiteDatabase._ensure_schema()` 做**幂等增量迁移**（`PRAGMA table_info` 检查列是否存在）：

```sql
ALTER TABLE user_profile ADD COLUMN user_id INTEGER REFERENCES app_user(id);
ALTER TABLE meal_record   ADD COLUMN user_id INTEGER REFERENCES app_user(id);
```

| 方案 | 说明 | 影响面 |
|------|------|--------|
| **A（推荐）** 两表加 `user_id` | 真正的多用户隔离，画像/记录按用户查询 | 大：A 聚合、B 记录工具、C 趋势图全部适配 |
| **B** 只加账号不改业务表 | 上线快，但多用户数据仍混存，隔离名存实亡 | 小 |

> 若不选方案 A，用户系统的价值仅剩登录/权限展示，数据隔离不成立，**不建议**。

### 2.3 版本与兼容

- `schema.sql` 头注释版本升为 `v1.1`
- 新库直接建含 `user_id` 的表；老库走 `ALTER TABLE` 迁移
- `_ensure_schema()` 中新增迁移逻辑：检查列 → 缺失则 `ALTER TABLE`（与 `init_db()` 幂等原则一致）

## 3. 认证方案

### 3.1 技术选型

| 方案 | 依赖 | 结论 |
|------|------|------|
| JWT（`python-jose` / `PyJWT`） | 新增依赖 | 推荐：无状态、前端易带、过期可控 |
| OAuth2 + FastAPI 内置 | 依赖同 JWT | 与 JWT 二选一，文档更标准 |
| **标准库 `hashlib.pbkdf2_hmac`** | 零新增 | **密码哈希推荐**：避免 `passlib/bcrypt` 兼容问题 |

**推荐组合**：`PyJWT` 签发 Token + 标准库 `pbkdf2_hmac` 哈希密码（零密码库依赖）。

### 3.2 接口清单

| 接口 | 方法 | 权限 | 说明 |
|------|------|------|------|
| `/auth/register` | POST | 匿名 | 注册，默认 role=user |
| `/auth/login` | POST | 匿名 | 校验密码，返回 JWT + 用户信息 |
| `/auth/me` | GET | 登录 | 返回当前用户信息 |
| `/auth/refresh` | POST | 登录 | 刷新 Token |
| `/auth/change-password` | POST | 登录 | 改密（需旧密码） |

### 3.3 Token 与中间件

- JWT payload：`{ sub: user_id, username, role, exp }`，有效期建议 24h
- 中间件解析 `Authorization: Bearer <token>`，注入 `request.state.user`
- **依赖注入**（`fastapi.Depends`）：
  - `get_current_user` → 登录态校验
  - `require_admin` → `role == 'admin'` 校验
- 现有匿名 `session_id` 保留为"游客模式"：未登录可对话，登录后会话绑定账号

| 能力 | 游客 | 用户 | 管理员 |
|------|:---:|:---:|:---:|
| 对话 / 推荐 / 天气 | ✔ | ✔ | ✔ |
| 查看本人记录 / 趋势 | — | ✔ | ✔（仅本人） |
| 设置本人画像 | — | ✔ | ✔ |
| 记录审批（HITL 确认） | — | 本人 | 全部 |
| 菜品 / 菜单管理（CRUD） | — | — | ✔ |
| 用户管理 / 全局统计 | — | — | ✔ |
| `/metrics` 运维指标 | — | — | ✔ |

### 实施要点

- `/records`、`/trend` 等按 `user_id` 过滤（方案 A 时）
- 管理员接口独立路由前缀 `/admin/*`，统一 `require_admin` 依赖
- 游客访问需登录的能力时返回 `401`，前端引导登录

## 6. 分阶段实施建议

### D8a：最小可用（认证闭环）

- 新增 `app_user` 表 + `_ensure_schema` 增量迁移
- `/auth/register`、`/auth/login`、`/auth/me` + JWT
- 中间件解析 Token 注入 `request.state.user`
- 现有接口**保持匿名可用**，不破坏现状

### D8b：数据隔离（最高风险，先行回归）

- `user_profile` / `meal_record` 加 `user_id`（方案 A）
- A 的聚合查询、B 的记录工具、C 的趋势接口全部按用户过滤
- **改动前先跑全部 A/B 测试确认基线，改动后全量回归**
- 现有记录（无 user_id）归属默认用户或保留可见

### D8c：管理端

- `/admin/*` 用户管理、菜品/菜单 CRUD、全局营养统计
- 前端：登录/注册页、路由守卫、角色路由

## 8. 风险与注意事项

- **Schema 唯一来源**：所有 DDL 变更必须在 `backend/db/schema.sql` 维护，B/C 只读适配
- **增量迁移幂等**：`_ensure_schema` 中 `ALTER TABLE` 须以 `PRAGMA table_info` 判空为前置，防止重复执行报错
- **密码安全**：绝不明文存储；PBKDF2 迭代次数建议 ≥ 100k；禁用弱密码
- **JWT 密钥**：放 `.env`（`JWT_SECRET`），不硬编码、不提交 git
- **测试隔离**：新表的增删改查测试遵循现有惯例（临时 SQLite + `_db_instance` 注入），不污染生产库
