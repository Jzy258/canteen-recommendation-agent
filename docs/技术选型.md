# 食堂菜品推荐与营养分析 Agent — 技术选型

> 版本：v1.1　|　日期：2026-08-01　|　状态：最终确定
> 本文档记录技术选型最终决策、理由与扩展方案，作为开发依据与答辩参考。

---

## 1. 选型原则

1. **1 周冲刺，风险优先**：优先砍掉"工程感强但集成复杂"的组件，把时间留给数据、Agent 链路、文档与测试。
2. **技术底线自证**：评分要求"至少 1 个 @tool 或 1 条 RAG 链路自己写"，因此核心链路（工具循环、RAG、评分公式、组合算法）**全部手写**，框架只做薄封装。
3. **前后端分离 + Docker 部署的工程观感保留**：答辩有"工程能力"展示点，但不因此引入过度复杂度。
4. **密钥不进库**：一律走 `.env`。

---

## 2. 总体技术栈

| 层次 | 选型（最终） | 关键作用 |
|---|---|---|
| AI / Agent 层 | Python 3.11 + **LangChain** + 手写工具/RAG 逻辑 | 工具调度、意图解析、多轮记忆 |
| LLM | **本地 LLM（Ollama 部署）**，可切换云端 API | 对话生成、工具调用、理由生成 |
| 后端 | FastAPI | 统一 API 出口、对接前端、承载中间件 |
| 数据 | SQLite（预留 MySQL 切换） | 菜品库 / 菜单 / 摄入记录 / 用户画像 |
| 检索 | 结构化查询为主 + 轻量向量/关键词 RAG | 菜品营养查询、近似菜品检索 |
| 前端 | **Vue3 + Element Plus + TypeScript** | 聊天界面、趋势图、操作引导 |
| 部署 | Docker Compose（含 Ollama 服务） | 前端 + 后端 + LLM 容器化，DEPLOY 依据 |
| 密钥 | `.env` + `python-dotenv` | 密钥/配置隔离管理 |

---

## 3. 分层选型详情

### 3.1 AI / Agent 层：LangChain + 本地 LLM

- **AI 层采用 LangChain**，负责：
  - Agent 编排与工具调用（`@tool` 声明、AgentExecutor / create_react_agent）
  - 多轮对话记忆（会话状态管理）
  - LLM 供应商抽象（本地 ↔ 云端可切换）
- **技术底线仍须守住**：评分要求"至少 1 个 @tool 或 1 条 RAG 链路自己写"，因此——
  - 至少 1 个 `@tool` 的业务逻辑（如推荐评分公式、组合优化算法）**由团队手写**，不抄样例；
  - **RAG 检索链路自研**（向量化 + 召回 + 排序），不依赖 LangChain 现成 RAG 模板；
  - 答辩时能讲清"工具如何被调用、RAG 如何召回"。
- **本地 LLM（Ollama）接入**：
  - 用 `langchain-ollama`（`ChatOllama`）连接本地模型；
  - 推荐选**支持 function calling 的模型**（如 `qwen2.5`、`llama3.1` 系列），避免推理型模型无法稳定返回工具调用；
  - 无 API 成本、数据不出本机、演示不依赖外网，是答辩/演示的稳妥选择。

### 3.2 后端：FastAPI（替代 SpringBoot）

| 对比项 | FastAPI（采用） | SpringBoot（参考栈） |
|---|---|---|
| 与 Agent 语言 | 同为 Python，单进程单语言 | 需跨语言 RPC/HTTP |
| 开发成本 | 半天出 API | 需独立构建、依赖、JVM |
| 集成点 | 1 个（前端↔FastAPI↔Agent） | 2 个（前端↔SpringBoot↔Python） |
| 1 周风险 | 低 | 高 |
| 工程观感 | 中 | 高（但非本课题重点） |

- **结论**：FastAPI 承担 API 出口、中间件（日志/耗时/Token 统计）、静态资源托管；SpringBoot 不引入。
- 若团队坚持"全栈工程风"，SpringBoot 仅做**薄壳**（鉴权占位 + 转发 + 日志），业务逻辑全留 Python。

### 3.3 数据：SQLite（替代 MySQL）

- **理由**：4 张表、单用户、演示场景，SQLite 零运维、免容器、迁移即拷文件。
- **保留扩展性**：数据访问层做薄封装，答辩可说明"可平滑切换 MySQL"。
- **表设计**（详见 DESIGN 文档）：
  - `dish`（菜品 + 营养 + 来源）
  - `menu`（5天×3餐菜单）
  - `meal_record`（每餐摄入，HITL 确认后写入）
  - `user_profile`（预算、偏好、忌口、历史营养汇总 → 兼作 Store 长期记忆）

### 3.4 前端：Vue3 + Element Plus + TS（最终确定）

- **确定采用 Vue3 + Element Plus + TypeScript**，配合 Vite 构建。
- 负责：聊天对话界面、营养趋势图表（ECharts）、预算/偏好设置表单、结果卡片与操作引导。
- **时间预算**：前端留足 2 天 + 与后端按 REST 契约联调；前 4 天优先保 Agent 链路，前端任务与后端并行推进。
- 备选说明：Gradio 仅作为"演示兜底"保留，一旦前端进度失控可快速切换，不阻塞整体。

### 3.5 部署：Docker Compose

- 服务编排：
  - `frontend`：nginx 托管 Vue 构建产物
  - `backend`：FastAPI（含 Agent / 工具 / RAG / 中间件）
  - `ollama`：本地 LLM 服务（模型挂载本地卷，避免重复下载）
  - `mcp-weather`：天气 MCP 独立进程
- 演示环境默认 `docker compose up` 一键启动；本地开发可跳过 Docker 直跑 Python。
- Docker 用于满足 DEPLOY 文档与"可拿出去用"的观感。

## 4. 参考栈对比与取舍说明

| 参考栈组件 | 决策 | 取舍理由 |
|---|---|---|
| Python + LangChain | **正式采用**（AI 层） | 工程化编排 + 供应商抽象；工具/RAG 逻辑仍自研保技术底线 |
| 本地 LLM（Ollama） | **新增** | 零成本、离线演示、不依赖外网，支持 function calling |
| SpringBoot + MySQL | **改为 FastAPI + SQLite** | 砍掉 JVM 服务与 DB 运维的 1 周内高风险项 |
| Vue3 + Element + TS | **正式采用** | 界面专业、答辩观感强，见 §3.4 |
| Docker 部署 | **保留（扩展为 4 服务）** | DEPLOY 文档 + 工程观感，见 §3.5 |

## 5. 评分标准对齐

| 评分项 | 本选型落实点 |
|---|---|
| ≥1 工具 / RAG 自己写 | 手写评分公式 / 组合优化 `@tool` 逻辑 + 自研 RAG 检索链路 |
| ≥2~3 工具 | `search_dish` / `recommend` / `optimize_meal` / `record_meal` / `get_trend`（LangChain `@tool`） |
| 多轮记忆、会话隔离 | LangChain 会话记忆 + Agent 层会话状态管理 |
| 中间件 + Token 统计 | FastAPI 请求包装中间件（日志 + 耗时 + token） |
| 子 Agent 或 MCP | 天气 MCP（Python 官方 MCP SDK） |
| Store 长期记忆 | `user_profile` 表持久化 + 对话注入 |
| Skill 文档 | 仓库内《菜品录入与推荐调用规范》 |
| Docker / DEPLOY | Docker Compose 编排 frontend + backend + ollama + mcp-weather |

## 6. 推荐项目结构

```
canteen-recommendation-agent/
├── backend/
│   ├── agent/            # LangChain Agent 编排、子 Agent、会话记忆
│   ├── tools/            # 工具层 @tool（检索/评分/优化/追踪，自研逻辑）
│   ├── rag/              # 菜品 RAG 检索链路（自研）
│   ├── llm/              # LLM 供应商适配（Ollama 本地 / 云端 API 可切换）
│   ├── middleware/       # 日志 / 耗时 / Token 统计中间件
│   ├── store/            # user_profile 长期记忆
│   ├── mcp/              # 天气 MCP Server（独立进程）
│   ├── db/               # SQLite schema + 数据访问（可换 MySQL）
│   ├── data/             # 菜品 / 菜单数据与清洗脚本
│   ├── main.py           # FastAPI 入口
│   └── requirements.txt
├── frontend/             # Vue3 + Element Plus + TS
├── docker/               # Dockerfile / docker-compose.yml（含 ollama）
├── docs/                 # 需求/设计/部署/分析/总结等文档
├── tests/                # 测试用例与结果
├── .env.example
└── README.md
```

## 8. 风险与应对

| 风险 | 应对 |
|---|---|
| LangChain 编排稀释"自己写"的证明 | 工具业务逻辑与 RAG 链路自研，答辩讲清实现细节 |
| 本地模型不支持/不稳定 function calling | 选用支持工具的模型（qwen2.5/llama3.1），并预留云端 API 切换 |
| 本地模型推理慢 / 显存不足 | 选 7B 级量化模型，Docker 挂载模型卷避免重复下载 |
| 真天气 API 卡在注册/配额 | MCP 默认走 mock 天气源，真 API 作可选开关 |
| Vue3 前端占用时间挤压核心功能 | 前 4 天优先保 Agent 链路，前端后置；极端情况退 Gradio 兜底 |
| 多服务集成点出问题 | 第一天定死 REST 契约，每晚集成，禁止超 1 天不合并 |

## 9. 可扩展性设计（为未来更多技术栈预留）

| 扩展方向 | 预留机制 |
|---|---|
| 切换/增加 LLM 供应商 | `llm/` 适配层统一接口（本地 Ollama ↔ 云端 DeepSeek/通义/OpenAI），LangChain 供应商抽象天然支持 |
| 数据库升级 MySQL / 向量库 | `db/` 数据访问层薄封装 + `rag/` 独立模块，可平滑替换 SQLite → MySQL / 引入向量数据库 |
| 前端换 Gradio / 增加移动端 | REST API 契约与前端解耦，前端可整体替换 |
| 新增 Agent 能力（更多工具/子 Agent） | 工具以 `@tool` 注册制，新增即注册；子 Agent 按模块扩展 |
| 天气 MCP 换真实天气源 | MCP Server 数据源接口化，mock ↔ 真实 API 可配置切换 |
| 部署扩容 | Docker Compose 服务编排可横向追加服务（如新增向量库、消息队列） |
